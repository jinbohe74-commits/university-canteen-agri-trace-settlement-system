# 第八轮改造：顶栏待办 + 入库确认清单

> 用户反馈两句话：
> 1. 「顶部栏待办这个功能形同虚设」
> 2. 「农户的入库确认这个功能为什么不显示所有待处理订单，要处理完一个才能看下一个」

这两条都不是"少一个按钮"，而是**入口和状态机的设计问题**。下面是取证过程和改法。

---

## 一、顶栏「待办」为什么形同虚设

### 取证

| 现象 | 代码位置 | 结论 |
|---|---|---|
| 农户、采购员的待办数字永远不显示 | `AppLayout.vue` 读 `store.user.pendingOrders / pendingInbound` | `LoginUser` 里根本没有这两个字段 → 恒 `undefined` → 徽标恒空 |
| 质检配送员的待办数字永远为 0 | `AppLayout.vue` | 压根没有 `INSPECTOR` 分支 |
| 点「待办」看不到待办 | `goTodo()` | 只是 `router.push`：管理员→预警页、农户→消息页、采购员→入库页、质检→任务页。**没说有几件事，也没说是哪几件** |
| 管理员数字勉强能看 | `adminApi.dashboard().todos.length` | 只有管理员一路有真实数据，其余三角色都是摆设 |

也就是说：这个按钮对 3 个角色是"点了一下，跳到一个页，然后你自己找"，对第 4 个角色连数字都是错的。

### 改法

**新增 `GET /api/common/todo-center`（`TodoCenterService`）**，按角色返回「组 → 条目」：

| 角色 | 分组（括号为数据源） |
|---|---|
| 管理员 | 结算单待审核（`settlement` 待审核）、订单逾期未接单（`orders` status=10 超期）、预警待处置（`warning` 待确认/待处理）、农户入驻待审核（`farmer` 待审核） |
| 农户 | 待接单（10）、待发货（20）、等质检抽检（30，仅知晓）、待结算（80，等放款）、已结算（仅知晓） |
| 采购员 | 待验收/入库（60）、在途订单（30/40/50，仅知晓）、待评价（100 且无评价记录）、需求处理中（按报价截止排序） |
| 质检配送员 | 待质检（30）、质检合格待配送（40）、配送中（50，仅知晓） |

三条设计原则：

1. **数字与业务列表页同源**——同一张表、同一状态字面量，不另算一套。
   实测：管理员 `37 = 结算 4 + 逾期 4 + 预警 23 + 农户 6`，与库表 `count(*)` 完全一致。
2. **区分「要你动手」和「只是让你知道」**——只有前者计入徽标。
   质检员的"配送中"、采购员的"在途订单"如果也进数字，徽标永远清不掉，用户立刻就不看它了。
3. **每条都带"等了多久 / 还剩多久"**——待办的价值是排优先级，不是罗列。
   结算单显示"已等 16 分钟"，逾期订单显示"逾期 34 天"，需求显示"剩 1 天"，超阈值的损耗率标红。

**新增 `TodoCenterDrawer.vue`**：点「待办」直接开抽屉，分组列出全部条目，点任意一条：

- 订单 / 结算单 → 打开**单据工作台**（字段 + 问题清单 + 时间线 + 当前角色可执行动作）
- 需求 / 预警 / 农户档案 → 落到对应页面

**配套**：换页时自动刷新待办数字；入库成功后立即刷新，避免"处理完一单，顶栏还写着 3"。

## 二、入库确认为什么"要处理完一个才能看下一个"

### 取证

`Inbound.vue` 首屏逻辑是 `loadPreview(orderNo)`，不传单号时后端

```java
qw.eq(Orders::getStatus, 60).orderByDesc(Orders::getCreateTime).last("LIMIT 1");
```

**只取一笔**。提交成功后前端 `data.value = null` 把页面清空，用户必须自己记住下一笔单号再手输。
等于把"今天还有哪些货要收"这件事交给人的记忆——库里同时有 14 笔待验收的订单。

> 说明：这个页面属于**采购员**（`purchaser01`），农户端没有入库确认。
> 但用户说的现象是真实存在的，按原话改。

### 改法

**新增 `GET /api/purchaser/inbound/pending`**（`InboundService.pending`），口径与预览自动取单完全同源（`status=60` + 本食堂），返回每笔的：订单号、批次号、产品、农户、数量、金额、**到货时间**、质检结论、**冷链温度**、是否超温 / 是否不合格。

**`Inbound.vue` 改成"待办清单 + 录入区"**：

- 顶部固定「待入库订单 N」清单，按到货先后排序（生鲜不能压着），每行显示异常标记（质检不合格 / 冷链超温）
- 点一行 → 右侧录入区切换，实收输入框自动获得焦点
- 标题显示「第 2 / 3 笔」，旁边有「先跳过，看下一笔」
- **提交成功 → 自动切到下一笔**并提示「已自动切到下一笔 X，还剩 N 笔待入库」；全处理完则明确说"已全部处理完"
- 扫码框保留，用于直接定位某一单（验收从通知/待办带 `?orderNo=` 进来也走这条路）

### 顺带修掉的一个更误导的问题

上一轮把「实收数量预填下单量」去掉了（否则点一下就是零损耗，实秤环节被绕过）。
去掉之后，未录入时 `receiveQty = 0`，页面就会算出**"损耗 400kg / 100% / 实结 ¥0.00"**——比预填更误导。

本轮加了 `hasReceive` 开关：未录实收时，损耗数量、损耗率、扣款、实结金额一律显示「待录入实收」，
确认入库按钮禁用；录入后才开始实时计算。

## 三、实测

### 待办中心（四角色，接口 + 页面双重核对）

| 角色 | 徽标 | 分组明细 |
|---|---|---|
| 管理员 | 37 | 结算 4 · 逾期 4 · 预警 23 · 农户待审 6 |
| 农户 farmer24 | 2 | 待结算 2（等放款）；等质检 1 条（仅知晓） |
| 采购员 purchaser01 | 12 | 待入库 2 · 在途 6（仅知晓）· 需求 10（其中 7 条无报价） |
| 质检 inspector01 | 5 | 待质检 2 · 待发车 3；配送中 1 条（仅知晓） |

### 入库页

- 待入库清单一次列出 3 笔（改前只有 1 笔）
- 实收填 390/400 → 损耗 2.5%、扣款 ¥58.90、实结 ¥2,297.10（实时计算正确）
- 未填实收 → 全部显示「待录入实收」，确认按钮禁用
- 提交成功 → 生成结算单 `JS20261111403`，清单 3 → 2，自动切到 `DD202610080312`
- 顶栏待办同步 13 → 12；管理员侧结算待审核 3 → 4（链路真实联动）

## 四、边界（如实说明）

1. **待办条目上限 60 条/组**，超出只显示前 60 条并在组头给出真实总数。生鲜系统单日不太可能超。
2. **需求「处理中」有 7 条是历史测试残留**（43 kg、无报价、内容雷同）。它们在待办里按"无报价 + 剩 1 天"标红，
   但这属于**数据**问题不是功能问题；清理需要一并处理关联报价，本轮没有擅自删库。
3. **入库确认属于采购员**，农户端没有这个页面。如果用户实际指的是农户侧某个环节，请指认页面，我按同一思路改。
4. `reform6` 里"点明细行下钻"原先硬编码 `farmer01` 的「待结算」卡片，该农户的订单已全部流转到已完成，
   卡片为 0 导致假失败。本轮改为**动态挑第一个有数据的指标**，不是放宽断言。

新增断言要点（都断言 DOM 可见，不只看接口 200）：

- 徽标数字 = 接口 `total`
- 点「待办」抽屉可见，且期望分组存在、条目数 > 0、文本无 `undefined/NaN`
- 点第一条 → 工作台可见并渲染字段/问题/时间线
- 入库页一次列出 ≥2 笔；点第二笔录入区与高亮同步切换；进度文案为「第 N / M 笔」
