# 第六轮整改说明（2026-11-11）

本轮反馈四项 + 一项要求：

> 1. 点击方框，同一界面的表格一样，没有看点
> 2. 有些表格还不能向右查看
> 3. 点击通知里面的「去处理」，只是跳转到结算审核这个界面，没有显示特定的问题
> 4. 点击待办亦是如此
> 5. 你自己模拟成这几个角色，去将所有功能试一遍，确实符合真实的管理信息系统和确保没有任何问题

这四项不是四个页面 bug，而是**同一个机制缺陷**：系统只做到「导航到列表页」，没做到「定位到具体业务对象并说明它有什么问题」。
所以本轮不逐页补按钮，而是补三套统一契约 + 一次四角色全量走查。

---

## 一、根因（取证到生成机制层）

| 反馈 | 表面现象 | 真实根因 |
|---|---|---|
| 方框明细与页面表格一样 | 点开抽屉就是同一张表 | `statDrill.js` 的 `DRILL` 注册表大量复用**页面同源列表接口**，且没有 per-metric 过滤；更隐蔽的是用「字段为空就保留」（`blank(x) \|\| ...`）兜底，导致筛选恒为「全通过」。`待质检 / 今日已检 / 不合格` 三个指标实际取的是同一份 `status=30` 待检列表 |
| 表格不能向右看 | 以为 CSS 禁了滚动 | 实测不是。真正原因三条：① Element Plus 横向滚动条默认 `opacity:0`，hover 才出现，用户无感知；② 全站 29 张表没有任何「还有右侧列」的提示；③ 4 个页面的 `.table-card { overflow:hidden }` 把滚动条边缘裁掉 |
| 通知「去处理」只跳页面 | 落到结算审核页，还要自己找单 | `openNotification` 只 `router.push(n.route)`，把通知里已有的 `bizNo / orderId` 丢了。待办同理，`todos` 只有 `path` |
| 状态像形式（上轮遗留） | 已入库/待结算只是标签 | 已在上轮补 `OrderStageActions`，本轮继续用统一工作台承接 |

## 二、改造内容

### 契约 1：单据工作台（Work Item）——「点哪里都落到这张单」

新增 `WorkItemService` + `GET /api/common/work-item`，入参只有 `{scope, todoKey, bizType, bizNo, orderId, keyword}`，
由后端查真实表组装出四段内容：

| 段 | 内容 | 数据来源 |
|---|---|---|
| `fields` | 订单号/批次号/订购量/金额/当前状态/下单时间 | `orders` |
| `issues` | **具体问题清单**：质检结论与抽检量、实收/损耗/损耗率与阈值、冷链温度、结算单待审金额、逾期天数 | `quality_report` / `inbound_record` / `delivery_order` / `settlement` |
| `timeline` | 订单创建 → 到货质检 → 发车配送 → 扫码交付 → 验收入库 → 生成结算单 | 同上，按真实时间排序 |
| `actions` | 当前角色能做什么（可带 `audit-pass` / `audit-reject` / `warning-handle` 直接执行，也可 `route` + `focus` 跳转并自动定位） | 按 `role` 裁剪 |

入口全部收敛到同一抽屉：

- 顶栏通知点击 → 原地打开工作台（**不再跳页面**），标题即「已入库待结算 · DD202611110360」
- 看板待办点击 → 工作台左侧列出「共 N 笔待处理」，可逐笔切换；结算待办可直接「通过审核 / 驳回重核」
- KPI 明细行点击 → 同一工作台

`scope=todo` 支持 `SETTLE / OVERDUE / CERT / QUALITY`，每类都返回**逐单**条目，不再是「11 笔待处理」一句汇总。

### 契约 2：指标分析视图（KPI 不再复刻列表）

`statDrill.js` 增加分析层，展示前对真实返回做「口径过滤 → 分组构成 → 汇总 → 异常洞察」：

- 概览：明细记录数、数量/金额合计、分组数、最大组占比
- 构成分析：按品类/状态/结论/农户等真实字段分组，条形图 + 条数 + 占比 + 合计
- 需要关注：不合格批次数、待处理数、高风险数、损耗率超 5% 数、已售罄数（**字段不存在就不生成，不臆测**）
- 明细行：只有真的带业务单号时才显示「单据 · 查看 ›」列并可下钻；货源/档案类不假装能点

指标口径逐个对齐统计 SQL，并新增专用明细接口补上原来没有明细来源的两个指标：

- `GET /api/inspector/quality-reports?today=1|unqualified=1` —— 今日已检 / 不合格
- 质检三指标现在分别是 `status=30`、`DATE(inspect_time)=CURDATE()`、`result='不合格'`，卡片数字与明细行数逐一相等

### 契约 3：表格横向可查看

- `tableHScroll.js`：用 `ResizeObserver + MutationObserver` 只在**真溢出**时给容器打 `has-hscroll`
- `global.css`：`.has-hscroll::after` 显示「↔ 本表还有右侧列：拖动表格下方滚动条，或按住 Shift 滚动鼠标滚轮」
- 横向滚动条改为常驻（`opacity:1; height:10px`），thumb 用主题色
- 4 个 `.table-card { overflow:hidden }` 改为可见溢出
- 抽屉里的明细表固定右侧「单据」列

### 第四项：四角色全功能走查

新增 `tools/reform6_acceptance.cjs`，四个账号逐页跑 31 个页面，同时断言：

- 无 `pageerror`
- 页面有真实内容（不是空白）
- 文案里不出现 `undefined / NaN / Invalid Date / [object Object] / null kg`（假数据哨兵）
- 农户访问采购员接口返回 403

## 三、过程中发现并修掉的缺陷

| # | 缺陷 | 根因 | 处理 |
|---|---|---|---|
| 1 | 工作台抽屉**永远不弹**，接口 200、控制台 0 报错 | `WorkItemDrawer` 把导出的 `workItemState` **函数**当状态对象用（`s.open` 恒 undefined）。L-049 的同类第 2 次，方向相反 | 改为 `const s = workItemState()`；验收脚本改为断言 DOM 可见，不再只信接口 200 |
| 2 | 「不合格」明细 0 行，卡片却显示 4 | `has(result, ['合格'])` 用子串判定，「不合格」包含「合格」 | 改前缀正则 `^(合格\|通过\|达标)`，`analyze()` 与 `FILTERS` 共用 |
| 3 | 待办 11 笔、工作台只有 8 笔 | 逐单查询 `LIMIT 8`，与统计口径不一致 | 上限放宽到 60，数字与看板一致 |
| 4 | 工作台时间线被裁在窗口里，右侧无可见滚动条 | `.wi-detail { max-height:68vh; overflow:auto }` | 去掉内层滚动，交给 `el-drawer` 自身滚动 |
| 5 | 左侧多笔待办列表被硬切一半 | 容器 `max-height` + 无渐隐 | 底部 22px 渐隐 + 细滚动条，明确「下面还有」 |
| 6 | 货源页第一屏全是「白萝卜 已售罄 0kg」 | ① 列表 `ORDER BY id DESC`，终态数据顶掉在售；② 端到端脚本每跑一次新建一条货源 | 排序改 `FIELD(status,'正常','已售罄','下架')`；`db/11_source_cleanup.sql` 三重收敛清理 5 条无订单引用的重复下架货源（先备份 `supply_source_bak_20261111`） |
| 7 | 质检报告明细 `orderNo` 取不到 | MyBatis `resultType=map` 不做下划线转驼峰 | SQL 里全部显式 camelCase 别名 |
| 8 | 工作台 `scope` 大小写敏感 | `switch("TODO")` 落到 default，把待办当通知 | `scope.trim().toLowerCase()` |
| 9 | 第五轮脚本「点通知跳业务页」变红 | 契约已改为原地打开工作台 | 更新断言为「原地打开且定位到同一单号」，不是回退功能 |

## 五、遗留边界（如实说明）

1. **工作台可见范围**：`ADMIN` 全量；农户/采购员按 `farmer_id / canteen_id` 过滤；质检员按批次作业可见全平台待检/在途单。跨角色越权由 `checkDataScope` 拦截，返回 403。
2. **`CERT / QUALITY` 待办的动作**是「标记已处置 + 去预警页」，不是自动修复证照或重检；系统里没有证照补传接口。
3. **历史测试数据**：本轮只清理了 5 条无订单引用、且同主体同品项存在更新记录的重复下架货源（已备份）。8 条 `DD2026111*` 白萝卜订单是真实走完的完整链路（含质检/配送/入库/结算），**没有删除**——删单会让库存与结算对不上。演示前如需干净环境，应重置数据库而不是删单条。
4. **表格横向提示**只在真溢出时出现；`订单监管`、`农户管理` 等 1440 宽下不溢出，因此不显示提示，属预期。
5. **KPI 明细最多取 50 行**（分析基于这 50 行），抽屉里明确写了「接口返回 N 条，按该指标口径筛得 M 条」，不假装是全集。
