# 第九轮改造：扫码交付误判 + 本批装载排版

> 用户反馈两句话：
> 1. 「质检员的配送任务界面的扫描交付明明正确输入了，却提示错误」
> 2. 「随车批次没排版好，显得界面不美观」

第一条不是"用户输错"，是**校验规则本身不可完成**。以下是从库表到代码的取证。

---

## 一、为什么"明明输对了却报错"

### 现场还原

弹窗里写：`应为：04****`；用户输入 `043455`；红字回：`批次尾号不符：应为 04****`。

右侧「随车批次」卡片当时挂着 15 个批次号，其中确有 `PC20261111F00010043455` ——**用户是照着这个列表抄的**。

### 库表取证

```sql
SELECT d.id,d.delivery_no,d.vehicle,d.status,o.batch_no
FROM delivery_order d JOIN orders o ON o.id=d.order_id ORDER BY d.id DESC LIMIT 6;
```

| 配送单 | 车辆 | 状态 | 订单批次号 | 末 6 位 |
|---|---|---|---|---|
| PS20261111423 | 赣H·D2791 | 待发车 | PC20261111F00010043455 | **043455** ← 用户抄的 |
| PS20261110416 | 赣H·D2688 | **配送中** | PC20261110F00020047599 | **047599** ← 本单实际 |
| PS20261110415 | 赣H·D2791 | 已送达 | PC20261110F00020047640 | 047640 |

结论：**两辆车、两个批次。页面把 15 个批次（跨 4 辆车）堆在一张叫「随车批次」的卡里，用户抄的是别车的批次。**

### 代码取证（两层根因，缺一不可）

| 层 | 位置 | 问题 |
|---|---|---|
| 提示不可完成 | `DeliveryService.view()`：`m.put("batchTailHint", mask(tail(batch,6)))` | `mask()` 只露前 2 位 → `04****`。后 4 位**照着界面永远凑不出**，任何"照页面操作"的人都必然失败 |
| 展示源≠校验源 | `Delivery.vue` 的 `batchList`：`records.filter(r => r.batchNo)` | `records` 是全部在途订单（40/50/60），不是本单。页面展示 A（15 条），后端校验 B（1 条），**抄 A 判 B** |
| 匹配过严 | `arrive()`：`expected.equals(given)` | 扫枪吐的是整串 18 位条码，手抄一般只有尾号；且空格/横杠/小写一律判错 |

一句话：**一个校验步骤，如果操作员只靠界面和现场实物无法确定通过，那就是设计缺陷，不是用户输错。**

## 二、改法

### 后端（`DeliveryService`）

1. `view()` 不再下发掩码，改为下发真实尾号 `batchTail`：
   ```java
   String batch = o.getBatchNo();
   m.put("batchTail", batch == null || batch.isBlank() ? null : tail(batch, 6));
   ```
2. `arrive()` 的判定抽成可单测的静态方法，归一化后三类输入都认：
   ```java
   public static boolean matchesBatch(String batch, String given) {
       String full = normalizeCode(batch);
       String code = normalizeCode(given);
       if (full.isEmpty() || code.isEmpty()) return false;
       return code.equals(full) || code.equals(tail(batch, 6))
               || (code.length() >= 6 && full.endsWith(code));
   }
   // normalizeCode：剔除 [^0-9A-Za-z] 并转大写
   ```
3. 错误文案改为**给出本单正确批次**，现场能自查是"扫错箱"还是"拿错货"：
   > 扫描到的批次与本单不符：本单批次 PC20261110F00020047599（尾号 047599），请核对货箱标签后重试

### 前端（`views/inspector/Delivery.vue`）

| 位置 | 改前 | 改后 |
|---|---|---|
| 第三张卡 | 「随车批次」15 条（跨 4 车）+ `word-break: break-all` | 「本批装载」= 本单 + 同车未完成批次（实测 1 条）；行内：`本单` 标签 / 整串批次号（单行省略、点击复制）/ `尾号 047599` / 品名·数量 / 装车时间 / 去向 |
| 当前任务卡 | 只有「复制批次号」按钮 | 增加一行 `随货批次 PC20261110F00020047599 尾号 047599`，不用打开弹窗就知道该核对哪串 |
| 扫码弹窗 | `应为：04****`（星号） | `本单批次 PC2026…7599 · 尾号 047599 · 复制`，说明改成"整串或尾号 6 位都认" |
| 输入框 | `maxlength="6"`（整串粘贴会被截断） | `maxlength="40"`，前端只挡 `<6 位`，其余交给后端判定 |
| 批次号排版 | 18 位定长串被撕成两行、撑破窄卡 | `white-space:nowrap + ellipsis + title`，卡片里只露尾号 6 位 |

排版细节：三张卡外框高度 321 / 285 / 246 px，差值 <90px；批次号 `scrollWidth == clientWidth`（无溢出）、`height < 30`（未换行）。

## 五、遗留

- 「运输节点」里 `到达 第一食堂 20:56` 这类时间是**预计节点**（发车 + 55 分钟推算），未完成时置灰；文案没区分"预计/实际"，看起来像未来时间。若你觉得别扭，下一轮可以改成「预计 20:56」并加一个实际到达时间的回填。
- 本单只有 1 个批次（数据模型是一单一批次）；卡片已按"多批次"渲染，真实一车多单时会同车并列显示。
