# 采购主流程改造说明（2026-11-10）

面向问题：「实际采购里没啥用，华而不实」。
这份文档记录改造前后的口径差异、改了哪些东西、怎么验证的、还有哪些边界没解决。

---

## 一、改造前的问题（先取证，再动手）

用真实角色把业务流程走了一遍，从库里取到的证据：

| 现象 | 取证 |
| --- | --- |
| 下单只能一品项一单 | `orders` 平均 `1.0000` 品项/单（332 单全部单行） |
| 需求与订单不连 | 有 `demand_id` 的订单占比 **0.3%**，需求发完就断了 |
| 报价数字是编的 | `purchase_demand.quote_count` 取「在售货源数」估的，库里没有任何报价表 |
| 没有库存 | 全库没有 `stock` 表，采购、入库、领用三者不闭环 |
| 证照附件 0% | 农户资质上传率 0，审核无据可依 |

结论：不是页面丑，是**业务链断在三处**——采购没聚合、需求没闭环、库存不存在。所以改的是数据模型和流程，不是皮肤。

## 二、三段改造

### 第一段：一单多品（购物车式下单）

**数据模型**：新增 `purchase_order`（采购单，一次提交一张），`orders` 加 `po_id` 指回采购单。

- 采购单：`po_no` / `canteen_id` / `purchaser_id` / `demand_id` / `item_count` / `total_amount` / `status`
- 履约子单仍是 `orders`，**一单一品项**，质检、配送、入库、损耗、结算的下游口径全部不动
- 历史 332 单按 `CG+日期+序号` 迁移成 332 张采购单，`orders.po_id` 全量回填

**提交逻辑**（`PurchaseOrderService`）：

1. 同货源重复提交先合并成一行（`LinkedHashMap` 累加数量）
2. **两轮循环**：先把所有品项校验完（货源存在 / 在售 / 报价 > 0 / 不超可供量），有任何一个不合格直接抛错，一个都不创建
3. 再逐项创建子单，整体一个事务——不会出现「买了 3 个成了 2 个」

**页面**：货源大厅卡片底部改成「数量 + 加入采购单」，底部吸底栏显示品项数 / 合计 / 品名摘要 / 到货时间 / 提交；`我的订单` 增加「按采购单 / 按履约单」双视图，采购单行可展开看子单明细。

### 第二段：需求 → 报价 → 订单打通

**数据模型**：新增 `demand_quote`（需求报价），`uk_demand_farmer` 保证同一农户对同一需求只有一条报价。

**流程**：

```
采购员发需求 → 农户在「需求大厅」看到 → 报价（单价/数量/送达天数/质量承诺）
→ 采购员打开需求详情看「报价比价」表（最低价、最高信用标记）
→ 定标 → 自动生成采购单 + 履约子单 → 农户接单
```

- `QuoteService.award` 里会校验需求归属食堂；原货源不可用时自动挂一条 `supply_source`（`origin_remark='需求定标自动挂牌'`），保证订单有货源可回溯
- 中标置「中标」、其余置「落选」、需求置「已成交」，`quote_count` 按真实行数刷新
- 历史假 `quote_count` 已清掉重算，并为「处理中」的需求补了真实报价行

### 第三段：库存、领用与采购建议

**数据模型**：新增 `stock`（食堂 × 品项唯一键）与 `stock_out`（领用流水）。

- **入库即入库存**：`InboundService` 确认入库后调 `StockService.addStock`
- **原子写**：入库 `INSERT ... ON DUPLICATE KEY UPDATE quantity = quantity + #{qty}`；出库 `UPDATE ... WHERE quantity >= #{qty}` 判影响行数，为 0 就是库存不足，不会扣成负数
- **采购建议**（`StockService.suggestions`）：

  ```
  日均消耗 = 近 28 天领用量 / 28
            （领用量不足同期到货量的 60% 时，改用近 28 天到货量推算，并标注「按到货」）
  安全库存 = 手填值；没填（0）时按 日均 × 3 天 自动兜底
  建议量   = 日均 × 7 天 + 安全库存 − 在库
  ```

- 「在库可撑 N 天」直接摆出来：不建议采购时用户能看懂**为什么**不建议（撑 28 天），而不是一句含糊的「无需补货」
- 一键把建议转成采购需求，接着走「农户报价 → 比价 → 定标 → 订单」

> 口径原则：日均只用库里的真实流水（领用或到货），不引入任何"假定消耗系数"；两个来源都没有就写「无消耗流水」，不猜。

## 四、顺带修掉的一个隐性缺陷

全站 218 处样式引用的是改版前的 `--c-primary` / `--c-muted` / `--c-border` 这套变量名，而新的 `tokens.css` 里没有定义。
CSS 变量未定义时，`border: 1px solid var(--x)` 这类声明会**整条失效**——边框直接消失、文字落回继承色，肉眼看只是"觉得哪里不对"。

已在 `tokens.css` 里加一段兼容别名集中映射到新 token，随主题自动切换，不再逐页改。

## 五、边界与遗留（写清楚，不藏）

1. **期初库存口径**：`stock` 的初始值取「近 30 天入库量」，只扣真实领用。领用流水是这次才有的，历史上没有，所以**期初偏高**（表现为「可撑 28 天」）。正确做法是上线时做一次盘点，用「出库 → 盘点调整」录入实际数。
2. **需求截止时间**：种子里「处理中」需求的截止时间原本全过期（10-26/10-27），农户永远报不了价；已统一 `UPDATE` 到未来 2~6 天，脚本每次重跑都会修。
3. **单据粒度**：采购单是"一次提交"，履约子单是"一单一品项"，所以按采购单看是聚合、按履约单看是明细，两个视图不要混着比数量。
4. **领用没有审批**：目前采购员点一下就扣库存，实际食堂可能需要班长确认，这一步没做。
